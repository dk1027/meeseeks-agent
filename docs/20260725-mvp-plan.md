# Minimal prototype plan

## Goal

Build the smallest end-to-end version of Meeseeks that can help a user author a task contract, independently inspect a local repository, run verification commands, and write a durable evidence-backed verdict.

The prototype succeeds when this workflow works in a small fixture repository:

```sh
meeseeks draft .meeseeks/example-task.toml
meeseeks verify .meeseeks/example-task.toml
```

The `/meeseeks.draft_task_summary` skill must provide the equivalent authoring workflow inside a compatible coding agent. Both entry points must produce the same versioned task format. Verification must produce a timestamped `verification_report.md` and preserve the output of every command it ran.

## Prototype boundaries

### In scope

- A local CLI with `init`, `draft`, and `verify` commands.
- A `/meeseeks.draft_task_summary` skill for conversational task and acceptance-criteria authoring.
- Shared task validation so CLI-authored, skill-authored, and hand-written contracts behave identically.
- Version 1 of the task TOML schema documented in the README.
- Discovery of project instructions from `AGENTS.md`, `CLAUDE.md`, and configured paths.
- One agent backend, behind an interface that does not expose provider-specific details to the verification workflow.
- Read-only repository inspection plus explicitly approved verification commands.
- Structured `complete`, `incomplete`, or `inconclusive` results.
- Markdown report generation and raw command-output artifacts.
- Fixture repositories that demonstrate all three verdicts.

### Out of scope

- Multiple concurrent verifier agents or consensus voting.
- Sandboxing untrusted commands beyond the execution controls supplied by the selected agent runtime.
- Automatic repair of incomplete work.
- A hosted service, GUI, telemetry, screenshots, or remote repositories.
- Skills other than `/meeseeks.draft_task_summary`.
- Packaging or publishing the full skills collection to a marketplace.

## Key design decisions

1. **The task TOML is the source of truth.** Parse it into typed internal models and reject malformed contracts before invoking an agent.
2. **The verifier returns structured data.** Require a machine-readable result containing the overall verdict, a result for every criterion, evidence, gaps, and commands run. Render Markdown from that data rather than trusting free-form Markdown.
3. **Evidence is durable and traceable.** Capture stdout, stderr, exit status, duration, and the exact command for every verification command. Report claims link to artifact paths.
4. **Runs are immutable.** Create a new timestamped run directory and never overwrite an earlier result.
5. **Provider integration is replaceable.** Keep prompt construction, tool execution, and result parsing behind an `AgentBackend` boundary, while implementing only one backend in the prototype.
6. **The verifier does not repair code.** Source edits are disabled during verification. A failed criterion becomes a reported gap.
7. **Authoring entry points share one contract.** The CLI, skill, and hand-written workflow all target the same schema and validator; the skill must not invent a second task format.

## Proposed architecture

```text
CLI
├── init
│   └── config and example task creation
├── draft
│   └── guided task and acceptance-criteria authoring
└── verify
    ├── task/config parser
    ├── project-context collector
    ├── verification orchestrator
    │   ├── agent backend
    │   └── command runner
    └── report/artifact writer

Skill
└── /meeseeks.draft_task_summary
    └── conversational authoring of the same task TOML contract
```

The agent receives the normalized task contract, project instructions, repository state, and access to read-only inspection and command-running tools. It must return a structured assessment for each acceptance-criterion ID. The orchestrator validates that response, derives the overall verdict where possible, and writes the report.

## Implementation phases

### 1. Scaffold the CLI and domain models

- Choose the implementation language and packaging layout.
- Add `meeseeks init`, `meeseeks draft`, and `meeseeks verify` command shells.
- Model configuration, task contracts, criterion results, evidence, and verdicts.
- Validate duplicate criterion IDs, empty descriptions, unknown schema versions, and missing task files.
- Add unit tests for parsing and validation.

Exit condition: a valid task loads into a normalized model and invalid tasks fail with actionable messages.

### 2. Implement task authoring

- Make `meeseeks draft [output-path]` guide the user through a title, description, observable acceptance criteria, out-of-scope behavior, and suggested verification commands.
- Support reviewing and revising the draft before writing it.
- Refuse to overwrite an existing task unless the user explicitly confirms it.
- Validate the completed task with the same parser used by `verify`.
- Create `/meeseeks.draft_task_summary` with instructions to inspect the current work when available, ask targeted questions where intent is ambiguous, and write the same version 1 TOML format.
- Have the skill distinguish observed implementation details from user-intended acceptance criteria instead of silently treating existing behavior as the specification.
- Add golden-file tests showing equivalent CLI- and skill-authored output.

Exit condition: both the CLI command and skill can create a schema-valid task that is accepted unchanged by `meeseeks verify`.

### 3. Create run directories and capture commands

- Generate filesystem-safe, timestamped run IDs.
- Implement a command runner that captures stdout, stderr, exit code, and duration without invoking a shell implicitly.
- Store one artifact per command and a small metadata manifest for the run.
- Refuse to overwrite an existing run.
- Add tests for success, failure, timeout, and unusual output.

Exit condition: configured verification commands run and their complete results are preserved under `.meeseeks/runs`.

### 4. Collect project context

- Discover `AGENTS.md` and `CLAUDE.md` from the working directory toward the repository root.
- Load additional paths from `.meeseeks/config.toml`.
- Record the instruction files used in the run manifest.
- Capture basic repository context such as root path, current commit, and changed files when Git is available.

Exit condition: the verifier input deterministically shows which task, instructions, and repository state were evaluated.

### 5. Integrate one verification agent

- Define the provider-neutral `AgentBackend` contract.
- Write the adversarial verification prompt and structured response schema.
- Give the backend repository-inspection and controlled command-execution capabilities.
- Validate that every acceptance criterion appears exactly once in the response.
- Convert backend failures, invalid output, ambiguous specifications, and unusable environments into an `inconclusive` result with a reason.

Exit condition: the backend evaluates a fixture change and produces a schema-valid assessment with cited evidence.

### 6. Derive verdicts and render reports

- Derive `incomplete` if any criterion is unmet.
- Derive `complete` only if every criterion is met with evidence.
- Use `inconclusive` if one or more criteria cannot be evaluated defensibly and none are known to be unmet.
- Render the report format documented in the README.
- Ensure all artifact links are relative and valid.

Exit condition: each fixture produces a readable report whose verdict agrees with its per-criterion results and whose evidence links resolve.

### 7. Prove the vertical slice

- Create three tiny fixture repositories or scenarios: complete, incomplete, and inconclusive.
- Add an end-to-end test for `init`, `draft`, and `verify`.
- Run a skill-authored task through the same verification fixture used for a CLI-authored task.
- Test paths containing spaces and repeated runs of the same task.
- Document installation, backend configuration, security expectations, and the prototype's limitations.

Exit condition: a new contributor can follow the README and reproduce all three verdicts locally.

## Suggested first milestone

Implement phases 1 through 3 without an LLM. Use a deterministic fake backend that reads a checked-in result fixture. This proves task authoring, schema validation, CLI behavior, artifact capture, verdict rules, and report format before provider integration introduces nondeterminism. The first skill can be exercised through golden conversational fixtures until an agent runtime is integrated.

## Open decisions before implementation

- Implementation language and packaging strategy.
- The first agent runtime/provider to support.
- Whether arbitrary task commands require interactive approval or must be allow-listed in configuration.
- Whether agent-authored exploratory tests may run from a temporary worktree in the prototype, or whether verification is limited to existing files and commands.
- The precise structured response schema and the minimum evidence required for a `complete` verdict.
